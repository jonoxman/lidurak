# T-95-1: Fix Quick Pairing Queue Semantics (Stay on Lobby Until Match Found)

## Background & Gap
Currently, clicking a Quick Pairing preset tile (e.g. `2P • 15s`) flashes the searching state for a split second and immediately creates/places the user into a new `WaitingForPlayers` room and navigates them to `/g/<gameId>`. Players waiting in the Quick Pairing queue must **not** be placed in an active room until enough players have matched; they must remain on the lobby screen with the searching status visible until a full match is formed (or until they cancel).

## Requirements
1. **Backend True Matchmaking Queue (`QuickPairingService` & `MultiplayerRoutes`):**
   - Refactor `QuickPairingService` so that `POST /api/quick-pair` enqueues the authenticated guest (`playerId`, `displayName`) into an in-memory waiting queue keyed by `(playerCount, turnTimeoutSeconds, allowRedirect)` instead of immediately creating a `GameRoom`.
   - Do **not** create a `GameRoom` or seat the player while the queue bucket has fewer than `playerCount` distinct players.
   - Return a typed queued response (e.g., HTTP `200` or `202` with `{ "status": "queued", "playerCount": ..., "turnTimeoutSeconds": ..., "allowRedirect": ..., "queuedCount": ... }`) when the player is waiting for more players.
   - If the same player submits `POST /api/quick-pair` again (same or different bucket), move/update their queue entry cleanly without duplicating them.
   - When the `playerCount`-th distinct player joins the same bucket, atomically dequeue all `playerCount` players, create a private `GameRoom` via `RoomManager`, seat all matched players in order (transitioning the room directly to `InProgress`), and:
     - Return `{ "status": "matched", "gameId": "<id>", "seatIndex": <idx> }` to the HTTP request that completed the match.
     - Push a real-time match-found notification (e.g., a targeted WebSocket event `{ "type": "quickPairMatched", "gameId": "<id>", "seatIndex": <idx> }` over `/ws/lobby` scoped to each matched `playerId`, or via a dedicated authenticated queue/lobby socket channel) to every waiting player in that match so they navigate immediately to `/g/<gameId>`.
   - `DELETE /api/quick-pair` must remove the authenticated player from any quick-pair bucket and return HTTP `204 No Content`.
   - Clean up any stale queue entry if a queued player disconnects their lobby socket or joins/creates another room directly, preventing ghost matches.
   - Keep `GET /api/games` / public lobby pool unaffected by queued quick-pair players (queued players must not appear as open rooms in the Lobby Pool).

2. **Frontend Quick Pairing Flow (`lobbyClient.ts`, `multiplayer.ts`, `QuickPairingTab.tsx` / `LobbyPage.tsx`):**
   - Update `lobbyClient.ts` and `multiplayer.ts` types to handle both `"queued"` and `"matched"` responses from `POST /api/quick-pair` as well as the `quickPairMatched` WebSocket event on `/ws/lobby`.
   - Ensure `/ws/lobby` is connected (or connects immediately when starting quick pairing) so waiting players reliably receive `quickPairMatched` while on the Quick Pairing tab—not only when the Lobby Pool tab is active.
   - When `POST /api/quick-pair` returns `"queued"`, keep the user on `/` (`LobbyPage`) displaying `[data-testid="quick-pair-searching"]` (`role="status"`, spinner, `"Searching for a <N>P • <T>s table…"` and `"Cancel"` button).
   - Clicking `"Cancel"` calls `DELETE /api/quick-pair`, clears the searching state, and keeps the user on `/`.
   - When `quickPairMatched` arrives over WebSocket (for waiting players) or `POST /api/quick-pair` returns `"matched"` (for the completing player), clear searching state and navigate via History API to `/g/<gameId>`.
