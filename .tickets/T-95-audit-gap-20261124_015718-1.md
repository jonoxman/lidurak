# T-95-audit-gap-20261124_015718-1: Deferred-Room Quick-Pairing Queue Semantics (Stay in Lobby Searching Until Match Found)

## Background & Gap
In QA feedback (#6), clicking a quick-pairing tile (e.g., `2P • 15s`) currently shows the searching state for a split second and immediately creates/joins a `WaitingForPlayers` room, navigating the player away from the lobby into `/g/<gameId>`. Players in the quick-pairing queue must **not** be seated in an active room until a full match has been formed; they must remain on the lobby screen displaying the searching indicator until all required players (`playerCount`) match, or until they click Cancel.

## Scope & Requirements
1. **Backend `QuickPairingService` Queue-First Matching (`backend/src/main/scala/durak/lobby/QuickPairingService.scala`):**
   - Maintain in-memory matchmaking buckets keyed by `(playerCount, turnTimeoutSeconds, allowRedirect)` storing queued `PlayerSession` / `(playerId, displayName)` entries **without** creating a `GameRoom` in `RoomManager` while the bucket has fewer than `playerCount` distinct players.
   - Deduplicate by `playerId`: if the same player is already queued (in the same or another bucket), remove/replace their previous queue entry so a single player can never match against themselves.
   - When a `POST /api/quick-pair` call does **not** yet complete a bucket (`queue.size < playerCount`), return a queued/searching result (e.g., `{ "status": "searching", "playerCount": ..., "turnTimeoutSeconds": ..., "allowRedirect": ... }` with no `gameId`).
   - Only when the `playerCount`-th distinct player joins the bucket:
     - Atomically dequeue all `playerCount` players from the bucket.
     - Create the authoritative room in `RoomManager` with all matched players seated (immediately starting in `InProgress` status with cards dealt; never appearing as an open public `WaitingForPlayers` room).
     - Return `{ "status": "matched", "gameId": "<id>", "seatIndex": <idx> }` to the triggering HTTP caller.
     - Broadcast a real-time match-found notification (e.g., `{ "type": "quickPairMatched", "gameId": "<id>", "seatIndex": <idx> }` routed per `playerId` over `/ws/lobby`, and/or a status check endpoint if needed as fallback) so every previously waiting queued player is notified immediately.
   - `DELETE /api/quick-pair` removes the authenticated `playerId` from any active queue bucket and returns `204 No Content`, leaving no orphaned rooms.
   - Clean up a queued player's entry if they explicitly cancel or leave (do not leave stale phantom queue entries across re-queues).

2. **Backend Routes & WebSocket Notification (`backend/src/main/scala/durak/http/MultiplayerRoutes.scala` and lobby WS hub):**
   - Update `POST /api/quick-pair` response encoding to support both `searching` and `matched` outcomes.
   - Ensure `/ws/lobby` authenticates the connecting guest session cookie (`lidurak_session`) so the lobby hub can deliver targeted `quickPairMatched` events to each matched `playerId` without leaking other players' private matches.

3. **Frontend Quick-Pairing Client & Lobby Flow (`frontend/src/api/lobbyClient.ts`, `frontend/src/types/multiplayerTypes.ts`, `frontend/src/components/lobby/QuickPairingTab.tsx`, `frontend/src/pages/LobbyPage.tsx`):**
   - Ensure the `/ws/lobby` WebSocket connection is active whenever a user is on the Lobby (not only while viewing the `Lobby Pool` tab) so `quickPairMatched` events are received immediately while on the `Quick Pairing` tab.
   - When the user clicks any quick-pairing tile (`[data-testid="quick-pair-2-15"]`, etc.):
     - Call `POST /api/quick-pair`.
     - If the response is `status: "searching"`, stay on `/` (`LobbyPage`), keep `[data-testid="quick-pair-searching"]` visible (`"Searching for a <N>P • <T>s table…"` with `.quick-pair-spinner` and `"Cancel"` button), and do **not** navigate away.
     - If the response is `status: "matched"` OR when a `quickPairMatched` event arrives over `/ws/lobby`, clear the searching state and navigate via History API to `/g/<gameId>`.
     - Clicking `"Cancel"` invokes `DELETE /api/quick-pair`, clears the searching state, and keeps the user on the lobby screen.
   - Verify no room appears in `Lobby Pool` while a player is merely searching in Quick Pairing.
